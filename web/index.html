Read the caveats before quoting these numbers

The 22.5× is against a naive process-per-request baseline. Against a competently configured FP16 resident baseline the honest figure is 3.38× decode + 2.32 GB RAM. INT4 quality was spot-checked at greedy decoding but not benchmarked on a task suite. Full list in Caveats and honest limits.

Context for the decode number

Jetson AI Lab reports 44.1 tok/s for Cosmos3-Edge on an AGX Orin 64 GB at BF16 via vLLM. This deployment reaches 76.0 tok/s on an Orin Nano 8 GB — the smaller, cheaper device — by moving to INT4 weights on the TensorRT-Edge-LLM runtime.

Live demo: measured on a quiesced board

Measured 2026-09-14 with the board doing exactly one job: cosmos3-edge-shim.service and live-vlm-webui.service running, everything else stopped. These are therefore uncontended numbers, and the procedure that produced them is listed below so they can be read for what they are.

The quiesce procedure — what was stopped

Stopped: Frigate, ring-mqtt, Mosquitto and Home Assistant (docker containers); frigate-notify, porch-feed, x11vnc, gnome-remote-desktop, jetson-oled, iperf3, kerneloops and fwupd (services). Left running: only the Cosmos3-Edge shim and the Live VLM WebUI. The effect was 6.73 GB used → 4.95 GB used, available 0.80 GB → 2.60 GB (1.8 GB freed), and load average 7.56 → 0.48.

Configuration the numbers were taken at

  • Power mode MAXN_SUPER (nvpmodel -m 2)
  • Engine loaded by the shim: /opt/tensorrt-edgellm/models/default — maxInputLen=1536, maxKVCapacity=2048, 28 decoder layers, hiddenSize=2048, INT4 W4A16
  • Workload: one 640×360 camera frame plus a one-sentence describe prompt, ~184–187 prompt tokens

The latency model

elapsed_ms = 200 + 13.49 × generated_tokens     # n = 2,818 real requests, r = 0.854

A 200 ms fixed term (image encode + prefill) plus 13.49 ms per generated token accounts for the whole observed range. The relationship is cleanly linear:

The spread is caption length, not instability

253 ms and 714 ms are the same engine at the same speed, on a short caption and a long one. The range above is not jitter, contention or thermal behaviour — it is the generated-token count moving, and the fit accounts for it. Quote latency alongside a caption length, or quote 13.49 ms/token instead.

Cross-check against an external number

The 74.1 tok/s measured here independently confirms this project's earlier 76.0 tok/s figure. Jetson AI Lab reports 44.1 tok/s decode for Cosmos3-Edge on an AGX Orin 64 GB at BF16 via vLLM; this is an 8 GB Orin Nano beating that, via INT4 self-quantization.

Measurement methodology

Two traps produced confidently wrong numbers before being caught, and both are easy to fall into.

Trap 1 — the encoder embedding cache

TensorRT-Edge-LLM caches vision-encoder embeddings keyed on raw pixel bytes. Benchmarking by looping the same image skips the entire ViT — about 250 ms of real work. Every probe here generates a unique image per iteration.

Trap 2 — contention with live traffic

The runtime serializes requests, so probes run against a live stream are inflated by whatever else is in flight. A "context cache regression" was reported and then retracted for exactly this reason. Under contention, minimums are the honest statistic.

Because response length varies per request, raw mean latency is not comparable across runs. The metric that works is a regression of latency against generated tokens:

elapsed_ms = fixed_ms + marginal_ms_per_token × gen_tok

This separates the two quantities that respond to different optimizations — fixed (preprocessing + ViT encode + prefill) and marginal (per-token decode). Final fit: R² = 0.999 over n=699 live requests.

Engine improvements

The campaign in brief — four rounds that shipped, one negative result that redirected the rest of them. Each is detailed in the sections that follow.

  • Round 1 — resident shim + CUDA graph capture + MAXN_SUPER clocks (GPU 306→1020 MHz, EMC 2133→3199 MHz): 13.91 s → 2.07 s (−85.1%). The largest single win, with no model changes: the original path shelled out to llm_inference per request, paying ~6–8 s of engine deserialization every single time.
  • Round 2 — micro-optimizations: context-cache reuse (−3.5%), greedy decode (−4.3%), and a real bug fix (req.top_k was never set, left zero-initialized instead of a validated 50). −4% total — below the threshold that was being held to.
  • Round 2.5 — a negative result, and the one that mattered most: it established that decode was memory-bandwidth-bound, not overhead-bound. At FP16 the model moved 3.36 GB per token in 43.29 ms = 77.6 GB/s against a ~102 GB/s theoretical peak — 76% of peak. No scheduling cleverness could help; the only lever with real headroom was making the weights smaller.
  • Round 3 — INT4 W4A16 self-quantization, round-to-nearest with an MSE-optimal clipping search, calibration-free: 43.29 → 13.38 ms/token; LLM engine 3.135 GB → 0.818 GB (3.83× smaller); process RSS 6.02 GB → 3.70 GB.
  • Round 4 — right-sizing the image token budget. With decode 3.2× faster the profile inverted and the FP16 vision tower became the bottleneck: the fixed term was 47% of mean latency, of which ViT encode alone was ~248 ms (26% of mean latency). Image tokens 512 → 320.

Converged at 13.13 ms/token.

How these are to be read

Round 1 — stop paying startup costs

The original path shelled out to a binary per request, paying engine deserialization (~6–8 s) every time. A resident shim holding one LLMRuntime for the process lifetime, plus CUDA graph capture and nvpmodel -m 2 + jetson_clocks (GPU 306→1020 MHz, EMC 2133→3199 MHz), took 13.91 s → 2.07 s with no model changes.

Round 2 — the round that failed, and why it mattered

Context-cache reuse (−3.5%), greedy decode (−4.3%) and a real bug fix (req.top_k was never set, leaving it zero-initialized) all landed below threshold. Reporting it matters because it established that decode was memory-bandwidth-bound: at FP16 the model moved 3.36 GB per token in 43.29 ms ≈ 77.6 GB/s against a ~102 GB/s peak. At 76% of peak, scheduling cleverness cannot help — the only lever left was making the weights smaller.

Round 4 — right-sizing the image budget

With decode 3.2× faster the profile inverted: the FP16 vision tower became the bottleneck, its 938 MB engine (larger than the INT4 text tower). The fixed term was 47% of mean latency, of which the ViT encode alone was ~248 ms — 55% of the fixed term and 26% of mean latency. Latency proved linear in image-token count, and the WebUI was pinned at the 512-token cap:

max_image_tokens_per_image is read at runtime from the engine's visual/config.json, so lowering it 512 → 320 needs no engine rebuild and is reversible in ~4 seconds. The effect was a constant −158 ms across every gen_tok bucket — the exact signature of a fixed-cost reduction.

How the INT4 quantization was actually done

The interesting part is that all three obvious routes were closed.

RouteOutcomeWhy
--quantization int4_awq✗ silent no-op Gated behind _needs_moe_quantization — MoE models only. Cosmos3-Edge is dense.
modelopt AWQ calibration✗ impossible attention_plugin is a custom op whose body is return torch.zeros(...) — a shape-only export stub. Eager forward yields zeros, so no activation statistics can exist.
Community INT4 checkpoint✗ declined ubr-physical-ai/Cosmos3-Edge-INT4-AWQ — its own docs state the checkpoint has never been executed.
RTN + MSE-optimal clipping✓ shipped Round-to-nearest needs no activation data at all, sidestepping the blocker entirely.

modelopt's real role here: format oracle, not quantizer

Its CUDA extension was broken on the host GPU (zeros in fp32, NaN in fp16), so INT4_BLOCKWISE_WEIGHT_ONLY_CFG was run on CPU purely to extract ground truth for the on-disk contract:

  • Scale convention scale = amax/7, q = round(w/scale).clamp(-8,7) — matched to 3.7e-09
  • Packing [N//2, K] uint8, two int4 nibbles per byte (even row low, odd row high)
  • weight_scale fp32 [N, K//128], per-output-channel per-group

Plain RTN gave 13.31% mean relative weight error. A calibration-free MSE-optimal clipping search (sweeping α ∈ [0.55, 1.0] per group, keeping whichever minimizes squared reconstruction error) cut it to 11.06%. 169 linears were quantized; the vision tower, projector, embeddings and norms stayed FP16.

Each stage was verified, because a silent quantization bug stays invisible until quality collapses: dequant round-trip error per tensor → nibble pack/unpack asserted to reproduce the tensor exactly → exported ONNX confirmed to carry 169 Int4GroupwiseGemmPluginV2 nodes and 100% non-zero weight bytes → engine reported Total Weights Memory: 865,480,704 vs 3,355,696,384, a 3.88× reduction.

Every optimization piece was already NVIDIA's

Not one optimization in this project required new NVIDIA technology. The resident runtime, the CUDA-graph decode, the INT4 matmul kernel, the on-disk quantization format contract, the runtime-tunable image-token budget, the power modes — all of it already shipped. What did not exist was the intersection: no published path takes this model, on this board, through these projects, to a measured number.

Two things this table does not claim

The contributor lists behind these projects are repo-level, not feature-level. NVIDIA/TensorRT-Edge-LLM in particular publishes squashed release drops — 26 commits for the whole project — so its history records who cut a release, not who wrote a feature. Being top contributor to CUTLASS is not evidence of having written Int4GroupwiseGemmPluginV2.

The stack is NVIDIA in its optimization path, not end to end. The quantizer in this repo runs on PyTorch and Hugging Face safetensors; the WebUI depends on aiortc, PyAV, OpenCV and the OpenAI client. Those are doing real work and are not NVIDIA's.

Run this yourself: the frozen one-shot branch

Everything above is reproducible in one pass from a freshly flashed board. oneshot/cosmos3-edge-live-vlm-webui carries an agent-executable runbook — eight phases, each with a gate that has a stated pass condition — scoped to Cosmos3-Edge and the Live VLM WebUI only. Point a coding agent at AGENTS.md and it runs end to end.

That branch is frozen and also tagged oneshot-v1, so the reference cannot drift as main continues. The gates are the substance: an all-zero quantized weight file exports and builds perfectly cleanly and only surfaces as garbage captions at the very end, so it is gated twice.

The specific gap this project hit

Jetson AI Lab lists Orin Nano 8 GB for Cosmos3-Edge but gives BF16-only guidance and no numbers. The TensorRT-Edge-LLM Orin Nano tutorial demonstrates INT4 AWQ — but on Qwen3-4B, not Cosmos3-Edge. Nobody documents the intersection: Cosmos3-Edge, quantized, on Orin Nano — exactly what an 8 GB board needs, and what an unexecuted community checkpoint was trying to fill.

Recommendations for cosmos-framework

First, a caveat on placement

cosmos-framework is today a training and inference framework, and the edge capability itself lives in TensorRT-Edge-LLM. The strongest version of this is not to relocate runtime docs, but to make cosmos-framework the authoritative index and contract owner — what is possible, what it costs, where to go — with deep links out. A thin accurate index beats a thick copy that drifts.

1. Publish a per-device support matrix with real numbers

The highest-value addition. Today you cannot answer "will this fit and how fast" without redoing this project.

Include the failures: Cosmos3-Edge-Policy-DROID does not fit on 8 GB. Knowing what doesn't work is as valuable as knowing what does.

2. Ship a validated, executed INT4 Cosmos3-Edge checkpoint

The community filled this vacuum with an artifact that has never been run. A first-party checkpoint with published provenance — method, calibration data (or explicitly none), measured weight error, benchmark scores — would displace it immediately. If shipping weights isn't viable, ship the recipe plus a verification script that asserts the packing contract and reports reconstruction error.

4. Document the measurement traps

Publish the embedding-cache trap and the fixed-vs-marginal decomposition. Without them users will generate confident, wrong numbers — and the support burden that follows is spent relitigating measurements.

5. Make the edge path discoverable

Add an "Edge / Jetson deployment" section to the README routing to TensorRT-Edge-LLM and Jetson AI Lab. Today the framework's inference story is Diffusers/Transformers/vLLM — which points an Orin Nano user at a path that will not fit.

6. Close the Orin Nano × Cosmos3-Edge gap specifically

Extend the Jetson AI Lab Cosmos3-Edge page with the Orin Nano 8 GB quantized path, and add a Cosmos3-Edge variant of the TensorRT-Edge-LLM Orin Nano tutorial (currently Qwen3-4B). Together that is the exact intersection nobody documents today.

Caveats and honest limits

  • Quantization quality is not fully characterized. 11.06% mean relative weight error (worst layer to_k at 20.5%) from uncalibrated RTN. Spot checks at greedy decoding look clean, but no benchmark suite was run.
  • No FP16-vs-INT4 side-by-side on identical prompts — both engines cannot be resident within 8 GB simultaneously.
  • Round 4's 20.8% is a quality tradeoff, not a free win — lossless on natural scenes, lossy on dense text.
  • The 22.5× headline compares against a naive baseline (process-per-request). Against a competently configured FP16 resident baseline, the honest figure is 3.38× decode + 2.32 GB RAM.

Reproducing this

# 1. Platform — free, largest payoff after the resident runtime
sudo nvpmodel -m 2 && sudo jetson_clocks          # MAXN_SUPER

# 2. Self-quantize the text tower — calibration-free, CPU, minutes
python3 rtn_int4_quantize.py --src <ckpt> --dst cosmos3_int4_ckpt

# 3. Export ONNX (host); build the engine ON the Jetson (TRT compiles per-GPU)
tensorrt-edgellm-export cosmos3_int4_ckpt cosmos3_int4_onnx --task reasoning --skip-visual
llm_build --onnxDir .../llm --engineDir .../reasoning \
          --maxBatchSize 1 --maxKVCacheCapacity 2048

# 4. Serve from a resident runtime — never process-per-request
systemctl start cosmos3-edge-shim.service

# 5. Right-size the image budget — runtime config, no rebuild, reversible
#    visual/config.json -> builder_config.max_image_tokens_per_image = 320

# 6. Measure honestly
python3 collect_perf.py "10 min ago"                    # fixed vs marginal
