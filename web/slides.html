Before optimizing — measure

Two traps that produce
confidently wrong numbers

Trap 1 — the embedding cache
The runtime caches vision embeddings keyed on raw pixel bytes. Loop the same image and you skip the entire ViT — ~250 ms of real work — and measure a fantasy.
Trap 2 — contention
Requests serialize. Probes run against live traffic are inflated by everything else in flight. A "cache regression" was reported and retracted for exactly this reason.

Both were hit. Both produced wrong conclusions first.

The metric that works

Separate fixed cost from per-token cost

elapsed_ms = fixed + marginal × gen_tok
  • fixed — preprocessing + ViT encode + prefill  →  attacked by Round 4
  • marginal — per-token decode  →  attacked by Round 3

Response length varies per request, so raw mean latency isn't comparable. Final fit: R² = 0.999 over 88 live requests.

Round 1 — the biggest win was free

Stop paying startup costs

  • The original path spawned a binary per request, paying 6–8 s of engine deserialization every time
  • Replaced with a resident shim holding one LLMRuntime for the process lifetime
  • capture_decoding_cuda_graph() to kill per-token launch overhead
  • nvpmodel -m 2 + jetson_clocks → GPU 306→1020 MHz, EMC 2133→3199 MHz

13.91 s → 2.07 s. No model changes. Do this before anything clever.

Round 2 — the failure that mattered

Why a −4% round is worth reporting

  • Context-cache reuse −3.5%, greedy decode −4.3%, a real top_k bug fix — all below the bar
  • But it proved decode was memory-bandwidth-bound, not overhead-bound
At FP16: 3.36 GB moved per token in 43.29 ms ≈ 77.6 GB/s against a ~102 GB/s peak — 76% of theoretical bandwidth.

At 76% of peak, no scheduling cleverness helps. The only lever left was making the weights smaller.

Round 3 — the method

modelopt as format oracle,
not as quantizer

Its CUDA extension was broken on the host GPU (zeros in fp32, NaN in fp16). So it was run on CPU purely to extract ground truth for the on-disk contract:

  • scale = amax/7 — matched to 3.7e-09
  • [N//2, K] uint8, two int4 nibbles/byte
  • weight_scale fp32 [N, K//128]
Calibration-free MSE-optimal clipping
Sweep α ∈ [0.55, 1.0] per group, keep whichever minimizes squared reconstruction error.

Plain RTN 13.31% → clipped 11.06% mean weight error.

169 linears quantized. Vision tower, projector, embeddings and norms stay FP16.

Round 3 — trust nothing

Four verification gates

  • Dequant round-trip error computed per tensor before packing
  • Nibble pack/unpack asserted to reproduce the quantized tensor exactly
  • Exported ONNX confirmed: 169 Int4GroupwiseGemmPluginV2 nodes, 100% non-zero weight bytes
  • Engine reported Total Weights Memory 865,480,704 vs 3,355,696,384 — 3.88×

A silent quantization bug stays invisible until quality collapses. The all-zeros failure mode had already been seen once.

The gap

Nobody documents
the intersection

Jetson AI Lab lists Orin Nano 8 GB for Cosmos3-Edge — but gives BF16-only guidance and no numbers.

The TensorRT-Edge-LLM Orin Nano tutorial demonstrates INT4 AWQ — but on Qwen3-4B, not Cosmos3-Edge.

Cosmos3-Edge, quantized, on Orin Nano is exactly what an 8 GB board needs — and exactly what an unexecuted community checkpoint was trying to fill.

Recommendations

Make cosmos-framework the index,
not a second copy

  • Per-device support matrix with real numbers — including what doesn't fit
  • Ship a validated, executed INT4 checkpoint — or the recipe plus a verification script
  • Preconditions per optimization — two of this project's dead ends failed silently
  • Document the measurement traps — or users will publish wrong numbers
  • Make the edge path discoverable — today the README points Orin users at vLLM
  • Close the Orin Nano × Cosmos3-Edge gap in the Jetson AI Lab page + tutorial

The capability lives in TensorRT-Edge-LLM. A thin accurate index beats a thick copy that drifts.

Caveats

What this does not claim

  • Quantization quality is not fully characterized. 11.06% mean weight error from uncalibrated RTN; spot checks clean, but no benchmark suite was run
  • No FP16-vs-INT4 side-by-side — both engines can't be resident in 8 GB at once
  • Round 4's 20.8% is a tradeoff, not a free win
  • 22.5× compares against a naive baseline. Against a competent FP16 resident baseline the honest figure is 3.38× decode + 2.32 GB RAM

3.38× decode
