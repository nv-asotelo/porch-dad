# INT4 contingency without an auxiliary GPU

Source review, 2026-09-20. **No verified, supported drop-in replacement for the current FP16 path was established.** CPU quantization without calibration is possible, but the exact Cosmos3 checkpoint format, model integration and answer quality still need validation. Evaluate FP16 first. This review performed no quantization, weight download, engine build or device operation.

The deployment references are NVIDIA TensorRT-Edge-LLM v0.10.1, revision `e8b29522938901f6df19ebeedd4b69bc8edbcd97`, and NVIDIA Cosmos3-Edge revision `344d602b128d1bbdacb43b08d0a3626f46343e29`.

## RTN is an algorithm; GPTQ can describe the storage format

Round-to-nearest (RTN) quantization does not acquire activation statistics from calibration examples. Writing its result into a GPTQ-compatible packed tensor layout does not mean the GPTQ optimization algorithm was used. A candidate must record the actual algorithm, producer, settings and export format separately. It must never be presented as calibrated AWQ.

The pinned NVIDIA quantization CLI exposes `int4_awq`, but no RTN export option; it accepts prequantized GPTQ checkpoints without creating them. Its direct builder recognizes `quant_method="gptq"` and `quant_method="awq"`, and ModelOpt `W4A16_AWQ`. Unknown methods, including `auto-round`, are rejected. Its `prepare_model` entry point also rejects ONNX model directories. Consequently, the presence of an INT4 ONNX export does not establish compatibility with our server's checkpoint-to-engine path. [NVIDIA quantization contract](https://github.com/NVIDIA/TensorRT-Edge-LLM/blob/e8b29522938901f6df19ebeedd4b69bc8edbcd97/docs/source/user_guide/features/quantization.md#L152-L168), [checkpoint parser](https://github.com/NVIDIA/TensorRT-Edge-LLM/blob/e8b29522938901f6df19ebeedd4b69bc8edbcd97/experimental/builder/core/quantization.py#L143-L194), [model resolver](https://github.com/NVIDIA/TensorRT-Edge-LLM/blob/e8b29522938901f6df19ebeedd4b69bc8edbcd97/experimental/server/runtime/engine_build.py#L113-L122).

## Reputable CPU RTN lead: Intel AutoRound

Inspected revision: `a5f6ddd8d05962fb197929c861aa3b7d2def4463`.

Intel documents CPU support, calibration-free RTN, and a regular `auto_gptq` exporter. That exporter records `quant_method="gptq"`, `provider="auto-round"` and `desc_act=False`, so its method metadata is recognized by our builder. This is a plausible integration lead, **not evidence that a Cosmos3 export loads correctly**. Model loading, selection of language layers, preservation of FP16 vision/projector, tensor names, packing and quality remain unverified. Pure RTN also lacks the activation-aware optimization of the intended AWQ candidate. [Intel usage and RTN documentation](https://github.com/intel/auto-round/blob/a5f6ddd8d05962fb197929c861aa3b7d2def4463/docs/step_by_step.md), [regular GPTQ-format exporter](https://github.com/intel/auto-round/blob/a5f6ddd8d05962fb197929c861aa3b7d2def4463/auto_round/export/export_to_autogptq/export.py#L301-L320).

The lightweight model-free path is not directly compatible: its INT output uses GPTQ-style packing with `quant_method="auto-round"`. Requesting plain `auto_gptq` falls back to the regular compressor/model-loading route. Merely rewriting the method label would bypass a guard without validating the artifact; no such change was made. [Model-free format contract](https://github.com/intel/auto-round/blob/a5f6ddd8d05962fb197929c861aa3b7d2def4463/auto_round/compressors/model_free.py#L53-L60), [format fallback](https://github.com/intel/auto-round/blob/a5f6ddd8d05962fb197929c861aa3b7d2def4463/auto_round/compressors/model_free.py#L2062-L2086).

## Public community checkpoint: unverified candidate only

`ubr-physical-ai/Cosmos3-Edge-INT4-AWQ`, inspected revision `0d7d69a34863557ae35e57bb68069c5712da77f4`, declares NVIDIA ModelOpt 0.45.0, `W4A16_AWQ`, group size 128, no quantized KV cache, and exclusions for visual, projector and embedding modules. Its card declares inherited OpenMDW 1.1 licensing. These are metadata observations, not tensor or license-compliance validation. [Quantization config](https://huggingface.co/ubr-physical-ai/Cosmos3-Edge-INT4-AWQ/blob/0d7d69a34863557ae35e57bb68069c5712da77f4/hf_quant_config.json), [model card](https://huggingface.co/ubr-physical-ai/Cosmos3-Edge-INT4-AWQ/blob/0d7d69a34863557ae35e57bb68069c5712da77f4/README.md).

September 10–11 card updates claim Orin execution, while the header and notes retain unexecuted statements. The authors describe fixes to an ONNX export workflow and unpublished calibration frames. Their reported workflow does not establish compatibility with our direct builder, and their performance or accuracy claims are not project measurements. Do not import their numbers into our results. [Author's deployment notes](https://huggingface.co/ubr-physical-ai/Cosmos3-Edge-INT4-AWQ/blob/0d7d69a34863557ae35e57bb68069c5712da77f4/JETSON_ORIN_NANO_NOTES.md).

The bounded provenance inspection covered the model card, both notes files and configs, plus the linked public `ubrobotics-ai/nvidia-codefest-2026` repository at `b0b9334721d36e5c4e37cea6dcc4b37ea14ce5c7`: README, INT4 quantization/export/run scripts, slice documentation and handoff. No `nv-asotelo` reference appeared in those inspected materials; no forbidden repository was accessed or used. The published quantizer wrapper imports NVIDIA's package and adds projector exclusions. This does **not** certify complete transitive provenance or reproducibility of unpublished inputs. [Published wrapper](https://github.com/ubrobotics-ai/nvidia-codefest-2026/blob/b0b9334721d36e5c4e37cea6dcc4b37ea14ce5c7/scripts/edge/int4_quant_fix.py).

Neither lead is a validated deployment recommendation. If pursued after FP16, retain a separate artifact and honest producer record, verify tensor binding/layout, and pass the same fixed visual quality workload before performance comparison. The existing bounded optimization rules still apply; no latency or memory benefit was measured here.
