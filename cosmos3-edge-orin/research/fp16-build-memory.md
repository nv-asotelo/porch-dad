# First FP16 build/load memory audit

Source audit only, 2026-09-20. No GPU build, runtime measurement, device change, or auxiliary GPU access occurred during this audit. The inspected TensorRT-Edge-LLM revision is `e8b29522938901f6df19ebeedd4b69bc8edbcd97` (v0.10.1); model revision is `344d602b128d1bbdacb43b08d0a3626f46343e29`. Target: P3767-0005 Orin Nano 8 GB, R39.2.1, CUDA 13.2 / TensorRT 10.16.2.

**Conclusion:** try the existing FP16 reasoner first, preferably building the cache in a separate process before starting the resident server. Upstream already avoids a full duplicate checkpoint in host memory. It still requires all final FP16 weights to remain resident. Temporary NVMe swap can relieve pageable CPU pressure; it cannot make the final CUDA allocations exceed physical DRAM. No workspace-cap flag exists in this experimental build path, and no particular cap is validated for this model.

## What the code actually holds

| Phase | Source-grounded behavior | Memory implication |
|---|---|---|
| Network construction | The server requests `--components all --externalize-weights all`. FP16 linears become shape/dtype descriptors plus checkpoint bindings. Components build sequentially. | No PyTorch model or full FP32/FP16 CPU clone is required by the direct builder. Physical shards contain extra generator tensors; the reasoner binding list does not request those tensors. |
| Checkpoint inspection | Safetensors shards are read-only memory mappings. Builder closes the weight store before `build_serialized_network`. Some small constants, including the visual position table, are materialized as FP16 via a temporary FP32 conversion. | Mapping the 7.7 GB of files is not equivalent to making 7.7 GB resident. Avoid claiming that every weight is external or that host allocation is zero. |
| TensorRT compilation | The builder creates a strongly typed network and default builder config, then builds serialized engines. Writing `bytes(serialized)` temporarily copies the serialized engine into a Python byte buffer. | Build-time host/device/tactic peaks remain unknown. Externalizing weights reduces what is embedded in the engine; it does not bound the optimizer's other allocations. |
| Weight loading | Each component allocates its full final GPU weight arena before materializing bindings. Ordinary BF16-to-FP16 identity conversion reads source windows of **32 MiB**, synchronizes, unregisters source memory, then discards completed mapped pages. | Source and destination coexist during conversion, but a full second reasoner checkpoint need not stay resident. Registered source windows consume shared DRAM temporarily. Final arenas remain allocated. |
| Resident initialization | Base weights load before base engine creation; KV/I/O resources follow, then visual runner weights. Execution context storage is shared between serial base/visual engines, sized to their **maximum**, not their sum. Server then captures decoding CUDA graphs. | Final weights + KV + I/O + maximum context requirement + graphs + runtime/OS overhead must fit. The existing server has no exposed graph-disable flag. |

## Practical first-attempt controls

1. Keep the existing reasoner-only snapshot, FP16, batch 1, no speculative decoder, one active request, input limit 1024 and KV capacity 2048. The verified 698 indexed BF16 tensors contain **4,871,240,160 bytes / 4.54 GiB**; FP16 has the same raw storage size. This is a weight calculation, not measured peak memory. Raw full-attention FP16 KV is **224 MiB** at 2048 tokens; allocator padding, page tables and other state are additional. See `results/model-download-validation.json` and the model configuration.
2. Build/cache first in its own process, then launch `scripts/run_backend.sh` with exactly the same model, cache and profile values. The normal server calls the builder inside its own process; there is no process boundary that guarantees release of build-time heaps/CUDA state before runtime initialization. A separate process is an operational precaution, not a measured gain. The upstream `prepare_model` function constructs the same cache and readiness marker; source [engine_build.py:407–452](https://github.com/NVIDIA/TensorRT-Edge-LLM/blob/e8b29522938901f6df19ebeedd4b69bc8edbcd97/experimental/server/runtime/engine_build.py#L407), matching [engine.py:710–741](https://github.com/NVIDIA/TensorRT-Edge-LLM/blob/e8b29522938901f6df19ebeedd4b69bc8edbcd97/experimental/server/runtime/engine.py#L710).

   Source-validated invocation shape, **not executed on target**; run from the pinned upstream checkout using its established environment and absolute local paths:

   ```python
   from experimental.server.runtime.engine_build import BuildOptions, prepare_model
   prepared = prepare_model(
       "/absolute/project/models/cosmos3-edge-reasoner",
       "/absolute/project/data/engine-cache",
       BuildOptions(max_input_len=1024, max_kv_cache_capacity=2048, max_batch_size=1),
       max_cache_size_bytes=12 << 30,
   )
   print(prepared)
   # Let this process exit before starting the resident server.
   ```

   Install `.[server,server-tools]` and pass the existing chat-template prerequisite first; do not create a generic-template cache. The first input should be one image and a short bounded answer.
3. If a recorded failure implicates CPU memory during compile/build, temporary project-owned NVMe swap is reasonable. Keep it out of persistent `fstab`; record its size and swap activity; remove it only after build processes exit and `swapoff` has enough RAM headroom. Preserve unrelated existing swap configuration. No swap was created in this audit. NVIDIA documents that pageable host eviction can free Tegra DRAM for device allocations and that `cudaMemGetInfo` does not count swap. The runtime's CUDA arenas and registered source pages still require physical memory. [CUDA for Tegra 13.2, §§3 and 3.3](https://docs.nvidia.com/cuda/archive/13.2.0/cuda-for-tegra-appnote/index.html#estimating-total-allocatable-device-memory-on-an-integrated-gpu-device).
4. If a recorded runtime allocation failure remains, a single smaller FP16 profile is a supported diagnostic: input 512 / KV 1024, still batch 1, with a prompt/image/output fitting those limits. This halves the calculated KV payload to 112 MiB; it does not halve model weights. The builder additionally supports image-token profile bounds via `BuildOptions(max_image_tokens=..., max_image_tokens_per_image=...)`; they are **not** resident-server CLI flags. Treat a changed visual profile as a separate cache/configuration. [Actual builder flags, cli.py:293–326](https://github.com/NVIDIA/TensorRT-Edge-LLM/blob/e8b29522938901f6df19ebeedd4b69bc8edbcd97/experimental/builder/cli.py#L293).

## Workspace cap: available API, absent upstream option

The direct builder never calls `set_memory_pool_limit`; neither its parser nor server `BuildOptions` offers a workspace field. Do not pass an invented `--workspace`, `--memPoolSize`, or environment variable. TensorRT's supported API is `config.set_memory_pool_limit(trt.MemoryPoolType.WORKSPACE, bytes)`. A future explicit patch immediately after `create_builder_config()` could trial **1 GiB** after a build OOM, but that number is an unvalidated diagnostic choice, not a guaranteed safe/fast setting. It restricts eligible tactic scratch space; it does not cap total process or GPU memory. `TACTIC_DRAM` is a separate optimizer pool, also not exposed here. A lower limit may leave no valid tactic.

The current official API documentation describes WORKSPACE's default as maximum device memory and embedded TACTIC_DRAM's default as 75% of device total memory; these are limits, not eagerly allocated amounts. The fetched current documentation is TensorRT 11.3; the same workspace API is documented in the archived TensorRT 8.6.1 Python API. Verify the actual installed 10.16.2 API and accepted pool limit before any patch, save the patch/diff, and use a fresh cache because this extra setting is not represented in upstream's cache options. No patch was made. [Current NVIDIA API](https://docs.nvidia.com/deeplearning/tensorrt/latest/_static/python-api/infer/Core/BuilderConfig.html), [archived NVIDIA API](https://docs.nvidia.com/deeplearning/tensorrt/archives/tensorrt-861/api/python_api/infer/Core/BuilderConfig.html).

Capture build and load separately: `/usr/bin/time -v`, `tegrastats`, `/proc/meminfo`, swap-in/out activity, allocation failures, and upstream's `peak mapped source`, `arena`, and `Setup shared execution context memory` log fields. Do not sum overlapping system/RSS/CUDA counters. Report FP16 fit as unknown until coherent image-grounded output succeeds; only then apply the fixed quality/performance workload and stopping rule in `GOAL.md`. Sustained inference swap activity is a rejection condition.
