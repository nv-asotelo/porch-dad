# Two Cosmos3-Edge hackathon implementations: source and evidence comparison

Reviewed 2026-09-21. This is a read-only comparison of the explicitly authorized public branch `oneshot/cosmos3-edge-live-vlm-webui`, frozen at **`1375886c6941caa6f43688e5945c036a584399fe`**, with this task's final selected MLP deployment at local commit **`796be230dea9cde3531f73ebc4abc6638dc3aeb5`**, branch `codex/cosmos3-edge-orin`. The latter commit freezes the runtime-controls/TTFT changes. It is published as [`935ea4887e19038e93be2bcbe19a5ecbe4777ec5`](https://github.com/nv-asotelo/porch-dad/commit/935ea4887e19038e93be2bcbe19a5ecbe4777ec5) on `codex/cosmos3-edge-mlp`, under `cosmos3-edge-orin/`; the subtree matches the local commit exactly. The companion [source-review receipt](../results/two-hackathon-branch-comparison.json) records hashes of the inspected files from these immutable commits. Only the authorized branch was fetched; its code was not run, copied into the implementation, or deployed. No unrelated personal or internal repository was accessed. The other branch's runbook was read as evidence, not executed as instructions.

Both projects make the public NVIDIA model work through TensorRT-Edge-LLM on an 8 GB Orin Nano. They make different choices about quantization scope, build path, clocks, image work, UI transport and validation. **Their published latency numbers do not establish a cross-branch speed ranking.** The useful comparison is what each implementation does and what its evidence actually measures.

## Timing definitions matter more than similar-looking numbers

| Evidence | Boundary | What can be said |

| One-shot shim `[perf] elapsed_ms` | `time.time()` immediately before reading request JSON through completion of the native answer; includes JSON/image decoding, preprocessing, executor/admission wait and full generation | A server handler duration. It is not native-only inference and not first-text latency. It excludes outbound response delivery, but request-body reading may still include inbound transfer. |
| One-shot40-request benchmark | Client `perf_counter()` around loopback HTTP POST and receipt of the complete JSON body | Complete-answer HTTP latency, including the shim's work and transport. No TTFT is available because this shim returns the whole answer. |

## Performance: reported history and independently checked measurements

The frozen branch records two different cohorts in one summary:

- **40 HTTP requests:** best249.2ms, median253.0ms, mean387.4ms, p90 623.9ms, maximum713.5ms; median14 generated tokens. This is a committed aggregate, not raw per-request records.
- **Separate2818-request live session:** reported model `elapsed_ms = 200 + 13.49 × generated_tokens`, correlation0.854, median442ms, best245ms, p90 607ms. The raw2818 journal rows and confidence intervals are not in the frozen tree. Correlation0.854 is not R²0.854. The report also describes another699-request cohort with approximately289ms fixed and13.13ms/token; it must not be silently merged with the2818-request fit.

Sources: [frozen aggregate](https://github.com/nv-asotelo/porch-dad/blob/1375886c6941caa6f43688e5945c036a584399fe/bench/live-webui-quiesced.json), [other reported cohort](https://github.com/nv-asotelo/porch-dad/blob/1375886c6941caa6f43688e5945c036a584399fe/docs/report.md#L93), [original regression implementation](https://github.com/nv-asotelo/porch-dad/blob/1375886c6941caa6f43688e5945c036a584399fe/scripts/collect_perf.py#L21).

**The40-request result is not demonstrated to be an uncached-frame benchmark.** Its committed harness loads one JPEG, reuses it for five warmups, then sends exactly the same payload40 times. The committed shim retains the native default encoder cache. That code is expected to permit repeated-image embedding reuse, although the historical executed state cannot be reconstructed solely from this aggregate. The later `oneshot/verify.sh` changes actual pixels per request to address that trap, but no corresponding raw run is committed. The branch openly documents the trap; its improved verification procedure does not retrospectively remove it from the earlier aggregate. [Repeated payload, lines108–135](https://github.com/nv-asotelo/porch-dad/blob/1375886c6941caa6f43688e5945c036a584399fe/bench/bench_live_webui.py#L108), [later varied-image verification, lines55–85](https://github.com/nv-asotelo/porch-dad/blob/1375886c6941caa6f43688e5945c036a584399fe/oneshot/verify.sh#L55).

The two projects did not share an evaluated corpus and rubric, so no quality ranking follows. ## What each contributed, and replay limitations

The one-shot work combines the stock runtime, an MSE-clipped RTN quantizer, resident service, actual Live VLM WebUI, a runbook with failure gates, and a useful account of cache/queue/response-length traps. It credits the public NVIDIA runtime/model/platform and Live VLM WebUI maintainers. The common substrate deserves the inference/kernel credit. The branch commit is authored by Alex Sotelo and carries a Claude Opus5 co-author trailer; that metadata records the published attribution, not a reconstruction of individual implementation effort. [Acknowledgements](https://github.com/nv-asotelo/porch-dad/blob/1375886c6941caa6f43688e5945c036a584399fe/ACKNOWLEDGEMENTS.md), [frozen commit](https://github.com/nv-asotelo/porch-dad/commit/1375886c6941caa6f43688e5945c036a584399fe).

The current work adds USB-C bring-up evidence, a direct-builder integration, independently authored RTN/storage validation, scoped compatibility repairs, a small MLP GEMV launch adjustment, compact retained capacities, original streaming UI, runtime per-image controls/cache isolation, matched acceptance and stop rules, request-correlated native timing, and tests/receipts. CUDA preprocessing, model architecture/weights, encoder/decode kernels and the main serving machinery remain public NVIDIA/upstream work. Reused upstream prompt text and layout/interpolation references are credited. [Contribution ledger](contribution-ledger.md), [third-party notices](../THIRD_PARTY_NOTICES.md).

Static review also finds gaps between the frozen one-shot **recipe** and its reported successful historical deployment:

1. The recipe supplies a modular checkpoint root to a quantizer that scans only top-level safetensors; no transformer-directory conversion is shown in that command path. [Runbook87–98](https://github.com/nv-asotelo/porch-dad/blob/1375886c6941caa6f43688e5945c036a584399fe/AGENTS.md#L87), [quantizer88–94](https://github.com/nv-asotelo/porch-dad/blob/1375886c6941caa6f43688e5945c036a584399fe/scripts/rtn_int4_quantize.py#L88).
2. It exports with `--skip-visual`, then asks the visual builder to consume a visual ONNX directory, without a visual export step in between. [Runbook122–148](https://github.com/nv-asotelo/porch-dad/blob/1375886c6941caa6f43688e5945c036a584399fe/AGENTS.md#L122).
3. Its tuning snippet writes a root-level image-budget key, while its report describes `builder_config.max_image_tokens_per_image`. That discrepancy needs reconciliation against the actual native configuration schema. [Runbook188–191](https://github.com/nv-asotelo/porch-dad/blob/1375886c6941caa6f43688e5945c036a584399fe/AGENTS.md#L188), [report470](https://github.com/nv-asotelo/porch-dad/blob/1375886c6941caa6f43688e5945c036a584399fe/docs/report.md#L470).
4. The new verification script warns, rather than fails, when the GPU is busy or timing is outside its band. Missing Pillow prints a warning and exits the Python timing block successfully. Its nominal marginal value assumes a200ms intercept instead of independently fitting it. A final verification PASSED line alone does not prove an uncontended, varied-frame regression. [Verification35–45 and55–102](https://github.com/nv-asotelo/porch-dad/blob/1375886c6941caa6f43688e5945c036a584399fe/oneshot/verify.sh#L35).

These are source-review findings, not claims that this branch was executed and failed. The current transfer package also does not include ready native binaries/engine caches or automatically recreate the selected MLP weights; its source-stage limits are explicitly documented. [Current deployment transfer scope](../docs/deployment-transfer.md).

## What would make a cross-branch performance comparison defensible

Freeze both artifacts and use the same board, power/clock policy, image bytes, prompt, requested sampling/output caps, actual visual work and cache state. Instrument both at the same post-JPEG, post-admission native boundary; retain a separate first-nonempty-text definition where streaming permits it. Measure several actual output lengths within each fixed input/cache stratum, retain failures/warmups/request IDs, and compare fitted slopes/intercepts with uncertainty. Evaluate captions on the same rubric, and sample system RAM/RSS separately. A source audit and historical aggregates cannot substitute for that experiment. **No such cross-branch run was performed in this review, and the deployed engine was not changed.**
