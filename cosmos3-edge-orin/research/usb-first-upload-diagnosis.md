# First RCM bulk upload: bounded diagnosis

Read-only investigation, 2026-09-19. No hardware operations or configuration changes were performed by this research subtask.

Observed evidence: [.qa/jetson-read-info.log](/Users/asotelo/Documents/ChatGPT/jetson-orin-streaming-codes/.qa/jetson-read-info.log) prints a BR_CID, then fails at the first `Sending bct_br`. The two log timestamps differ by 5.7 ms; that is the guest tool's reported timing, not a measured host USB timeout. Host [USB trace](/Users/asotelo/Documents/ChatGPT/jetson-orin-streaming-codes/data/flash-host/usb-trace.log) subsequently shows successful `GET_DESCRIPTOR` requests (`0x8006`, string descriptor value 771), then bulk OUT endpoint 1, length **8192**, followed by cancellation without a successful bulk completion. Therefore UID success proves descriptor/control communication; it does **not** establish bulk transport. EEPROM/SKU fields printed after the failed command are error text, not board identification.

## What the public implementations establish

QEMU v11.1.1 allocates a transfer and submits bulk OUT without setting `LIBUSB_TRANSFER_ADD_ZERO_PACKET`; its bulk timeout is unlimited. Its driver-detach loop probes all possible interface numbers, explaining why nonexistent interfaces can produce `NOT_FOUND`. Closing a passed-through device aborts transfers, releases interfaces, resets the USB device, and closes the handle. `guest-reset=off,guest-resets-all=off` suppresses guest-triggered resets but **does not suppress the reset on device close**. [QEMU implementation, especially lines 1026, 1210, 1433 and 1530](https://raw.githubusercontent.com/qemu/qemu/v11.1.1/hw/usb/host-libusb.c).

Libusb v1.0.29 Darwin submits bulk OUT through `WritePipeAsyncTO`. It implements `ADD_ZERO_PACKET` by sending an additional zero-length write **after successful completion**; the generic API page's Linux-only statement conflicts with this implementation. Darwin reset uses `ResetDevice` for a captured device or re-enumeration/restoration otherwise. Darwin returns `NOT_FOUND` for a nonexistent interface registry entry. These are source findings; the installed host library version must be distinguished from this inspected tag. [Darwin source, lines 1989, 2042, 2077 and 2376](https://raw.githubusercontent.com/libusb/libusb/v1.0.29/libusb/os/darwin_usb.c).

NVIDIA documents the same first-`bct_br` error and recommends a fresh recovery session after disabling Linux USB autosuspend. Its IGX Orin guide explicitly says a power cycle is needed to clear that condition. This is related Orin evidence, not proof that the present macOS passthrough failure has the same cause. [Jetson AGX Orin FAQ](https://forums.developer.nvidia.com/t/jetson-agx-orin-faq/237459), [NVIDIA IGX USB timeout guidance](https://docs.nvidia.com/igx/user-guide/1.0/troubleshooting.html#usb-timeout-error-during-flashing).

## At most two diagnostic changes

1. **One controlled APX detach/re-capture, with guest-triggered resets disabled.** After the existing read has stopped, remove only its `usb-host` device, wait for deletion/cancellation, then re-add the same physical device using `guest-reset=off,guest-resets-all=off` and logging configured at realization. Preserve the VM/disk/controller setup. This tests whether reopening/resetting the macOS interface resolves stale transport state while avoiding another guest reset. Re-enumeration may change the host USB address. Run one bounded board-read and require an actual 8192-byte OUT completion and valid output files. This is an inference from the implementations, not an established Jetson fix.
2. **If unchanged, one fresh power-cycle into force recovery with guest USB power management disabled.** Confirm the APX guest device's `power/control=on` and disable guest USB autosuspend before this single retry. Physical power cycling and force-recovery entry need the primary agent/user's hardware action; a software USB reset is not documented as equivalent. Stop further warm retries if the same first bulk transfer fails.

Do not change ZLP flags, allocate a 2 GB usbfs buffer, or rebuild QEMU based on this trace. The first transfer is only 8 KiB, there is no successful bulk completion to support an end-of-transfer ZLP diagnosis, and no `ACCESS` error has been shown to justify elevated host execution. A repeated failure after the two diagnostics establishes a blocked macOS passthrough path for this setup, not defective Jetson hardware. A native supported Linux host would then be the discriminating comparison.
