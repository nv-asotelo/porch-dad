# Initrd USB publication versus QEMU attachment

Read-only source investigation, 2026-09-20 UTC. No device commands, UI interactions, security changes, resets or hardware mutations were performed by this subtask.

The primary agent reports that the 104MB RAM recovery image transferred and the Jetson changed from APX `0955:7523` to `0955:7035`, named `Linux for Tegra`. macOS `ioreg` describes the new device as `!registered, !matched, active, busy 0`; it has no child interfaces or new host network interface. QEMU `info usbhost` and the guest omit the new device. The host's initrd wait timed out while the RAM system's USB device remained present. The primary agent retains the hardware observations in [ram-recovery-boot.json](/Users/asotelo/Documents/ChatGPT/jetson-orin-streaming-codes/results/ram-recovery-boot.json).

**This points to incomplete macOS device publication, earlier than guest attachment. Accessory approval is plausible, but not yet proven.**

Apple's public IOService state masks define inactive=`0x1`, registered=`0x2`, matched=`0x4`. Therefore `IOServiceState=0` is consistent with the observed unregistered/unmatched/active text; it is not an authorization result or proof that USB power is off. Apple's source explains that first-match notifications follow driver matching. [Apple IOService definitions and notification contract](https://github.com/apple-oss-distributions/xnu/blob/main/iokit/IOKit/IOService.h), [Apple ioreg rendering](https://github.com/apple-oss-distributions/IOKitTools/blob/main/ioreg.tproj/ioreg.c)

libusb 1.0.29's Darwin backend enumerates through `IOServiceGetMatchingServices` for `IOUSBDevice` and subscribes to `kIOFirstMatchNotification` for arrivals. It then creates the device user-client plug-in and caches the descriptor. The reported unmatched device has not reached this normal publication path. More precisely, this is about the **device service**, not a claim that a USB interface must already be claimed by a network driver. No public numeric mapping was established for `UsbEnumerationState=2` or this driver's `CurrentPowerState=2`; neither should be labeled “approval denied” from these numbers alone. [Pinned libusb Darwin source](https://github.com/libusb/libusb/blob/v1.0.29/libusb/os/darwin_usb.c#L506)

QEMU 11.1.1 `hmp_info_usbhost` lists every non-hub device returned by libusb with a readable descriptor, independent of the configured passthrough VID/PID filters. Its separate automatic-attachment path applies those filters and retries on a two-second timer. An old `productid=0x7523` filter would prevent guest attachment of `0x7035`, but **does not explain its omission from `info usbhost`**. A stale libusb context remains a secondary possibility if a fresh standalone enumeration can see the device after publication. [Pinned QEMU source](https://github.com/qemu/qemu/blob/v11.1.1/hw/usb/host-libusb.c#L1834)

## Least-disruptive next step

Keep the Jetson powered and its current RAM boot intact. On an Apple Silicon **Mac laptop**, Apple documents a prompt for a new or unknown USB accessory and requires the Mac to be unlocked before approval. The changed product identity could be treated as new; this is an inference, not a documented guarantee about Apple's identity cache. Have the user unlock the Mac and choose **Allow** if a `Linux for Tegra`/NVIDIA accessory prompt appears. The primary agent has already asked for this. Keep the existing accessory security policy; neither a global “Always allow” change nor privileged driver unloading is needed for this check. [Apple accessory approval instructions](https://support.apple.com/en-gb/102282)

After approval, recheck publication and fresh libusb visibility. If the device becomes registered/matched and appears in QEMU's host list, attach the exact `0955:7035` identity and resume the existing RAM-system inventory path. If a fresh libusb enumeration sees it but QEMU does not, investigate QEMU's cached context/hotplug handling. If it remains unregistered in macOS, changing QEMU filters cannot repair that layer; preserve this evidence and investigate the host's enumeration/approval failure. Avoid another cold power cycle at this stage because it would discard the current RAM boot.
