# Follow-up latency goal under Live VLM defaults

This experiment follows the completed initial four-trial search and the user's correction to match Live VLM WebUI defaults. The earlier search used 512×512 images, a 64-token ceiling and greedy decoding. Its results remain historical; they are not the denominator here.

The user-set active goal is: “Improve the Cosmos3-Edge inference to get a minimum of 10% improvement each time in terms of latency. Stop improving when you can no longer get 10% improvement from the last run.” The agent implemented that stopping rule as the first confirmed measured candidate failing the 10% gate. The three-image suite, geometric mean, five warmups and 30 measurements are agent-selected controls, not verbatim user requirements. The [contract](../results/latency10/plan.json) was frozen before measurement. It uses equal weighting through the geometric mean of three per-image median complete-answer latencies. Each configuration gets five warmups and 30 measured requests per image. Every measured answer, actual completion count and normal stop must match. No errors, OOM or swap I/O are allowed, and at least 512 MiB shared RAM must remain available.

## Workload and baseline

Three [frozen inputs](../benchmarks/live-vlm-1280/manifest.json) contain the action camera, pen and scissors from the user's recording. These are camera-preview crops encoded to 1280×720 JPEG 0.75 by Chromium, not original sensor frames or the exact historical inference inputs. Both configurations receive identical bytes and the prompt “Describe what you see in this image in one sentence.” The ceiling remains 512 tokens and temperature 0.7. The request omits top-p/top-k, which resolve to the unchanged native 0.9/50. The existing native sampler uses seed 42/offset 0; repeatability was measured rather than assumed.

Inference runs serially through the Orin-local UI proxy. Timing includes image decode, inference and streamed output. Browser capture/encoding, Wi-Fi and the every-30-frames scheduling cadence are outside this isolated measurement. The live webpage keeps that default scheduling behavior.

The fresh baseline produced identical outputs across all repeats, with actual completion counts 14/40/17. Complete-answer medians were 1004.572/2151.126/1152.300 ms for action camera/pen/scissors; the equally weighted geometric mean was 1355.410 ms. All 90 measured requests succeeded. See [baseline assessment](../results/latency10/baseline-summary.json).

The action-camera answer adds an unsupported mirror claim, and the pen answer infers gesture meaning and body-side details. Preserving these outputs establishes runtime equivalence, not correctness. This three-image set does not establish representative visual accuracy.

## Original experiment and upstream contribution

NVIDIA's public TensorRT-Edge-LLM supplies the model runtime, CUDA kernels, top-K/top-p sampler and RNG behavior. The task-authored candidate retains each thread's partial maximum between successive top-K selections and rescans only the winning thread's partition. It keeps the original partition, scan order, comparisons, reductions, temperature arithmetic and stage-two sampling. No weights, generation settings or image dimensions change; no image embeddings or answer text are reused between requests.

The standalone profiler measured the original sampler at about 0.262 ms per call on synthetic fixed logits. That is not an actual per-token model trace or an end-to-end speedup. It suggests limited latency headroom, which the full comparison must confirm. A paired GPU harness checks stage-one indices, FP32 value bits, temporary logits, guard regions and final sampled tokens on controlled FP16/FP32 fixtures. All 338 GPU cases passed, comparing 163,328 indices and FP32 value bit patterns, 22,996,778 scratch-value bit patterns, and 1,020 sampled tokens. The initial profiler runs had different model-residency states, so both saved standalone binaries were replayed with the same idle, loaded service and 1,000 warmups each. The controlled synthetic means were 0.261280 ms per call for the baseline and 0.203009 ms for the candidate (22.30% lower), with 1,000 measured calls each. These CUDA-event batch measurements are not a model trace or the whole-answer acceptance metric. Initial receipts remain preserved. The native incremental rebuild took 42.21 seconds without OOM or swap activity.

The first harness link encountered duplicate CUDA device symbols: including the original source and linking the runtime archive also brought in its sampler object. The recovery wrapper restored the original runtime. The test now removes the redundant sampler object from a separate archive copy; the serving archive is preserved. This is a test-build correction, not a performance result or user intervention.

## Final result

The full candidate comparison preserved every measured answer and completion count. It produced geometric-mean median latency **1348.917 ms**, versus **1355.410 ms** for the baseline: **0.48% lower**, below the frozen 10% gate. The per-image medians were 997.263 / 2144.403 / 1147.729 ms. All 90 measured candidate requests succeeded, with no OOM or swap activity. Both configurations had exactly the expected 105 backend POSTs including warmups; each was idle with no queued requests afterward.

Sampled shared system RAM peaked at **6.443 GiB baseline / 6.420 GiB candidate**. Process RSS peaked at **5.909 / 5.897 GiB**, which overlaps the system counter and must not be added to it. Minimum available shared RAM was **0.926 / 0.949 GiB**. These are extrema across warmup and measured requests, not dedicated VRAM allocations.

The only failed acceptance gate was the 10% whole-answer threshold. No repeat was needed because 0.48% is far below that threshold; the small observed difference is not presented as a robust general speedup. The search stopped after this candidate. The original FP16 source, object/archive and runtime library were restored from the verified task backup, preserving the initial runtime SHA256. The prototype patch is retained as an experiment, **not installed in the selected service**. This is a bounded search outcome, not proof that no future optimization could exceed 10%.

All three post-restoration images matched the baseline again; both services are active, and the backend is idle with zero queued requests.
