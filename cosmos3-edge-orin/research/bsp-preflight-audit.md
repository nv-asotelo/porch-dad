## Prerequisites by stage

1. **UID:** complete official `bootloader/tegrarcm_v2`, Linux USB device access to the APX device, and the correct chip argument. Rootfs, CUDA, a flashed OS, SSH and storage media are not involved in the source's UID command. The ordinary Orin tool's ELF/program headers confirm a **statically linked ELF32 Intel i386 executable**. The same is true for `chkbdinfo`, `tegrabct_v2`, `tegraparser_v2`, `tegrahost_v2`, `tegradevflash_v2` and `mkbootimg`; bundled `kernel/dtc` is static ELF64 x86_64. An x86_64 Linux guest needs IA32 execution support for the 32-bit tools; their inspected headers have no dynamic interpreter requirement. A macOS ARM64 process cannot run these Linux ELFs natively. `file`'s missing-section-header note is expected because only 4,096 header bytes were extracted.
2. **Board EEPROM/read-info:** complete BSP bootloader tools, the actual board `.conf` and common configuration, `kernel/dtb` directory, and matching T234 applet/BCT/fuse-read assets. The complete archive already supplies `kernel/dtb`, `readinfo_t234_min_prod.xml`, `mb1_t234_prod.bin`, `psc_bl1_t234_prod.bin`, `mb2_t234.bin`, `applet_t234.bin`, `fuse_t234.xml` and the P3767 diagnostic-boot/device/misc/min-ratchet BCT sources. No `apply_binaries` step is needed to create these. `flash.sh` validates the DTB directory before option processing at 3067; EEPROM files are selected at 3589–3601. The early read-info path exits before rootfs/image setup at 3818. Generating the read script uses Bash/GNU core tools and the UID helper; **executing** it also needs Python 3, **PyYAML** (unconditionally imported by `tegrasign_v3_util.py:24`), `cpp`, bundled DT/compiler/signing/native tools including `tegraopenssl`, and USB permissions. Neither a populated rootfs nor CUDA is required by this path. Secure-boot-fused boards can additionally require the corresponding authorized keys; do not bypass their checks.
3. **Initrd inventory:** complete matching BSP and populated R39.2.1 sample rootfs with NVIDIA binaries/modules applied. `generate_rcmboot_flashingcmd` invokes `flash.sh -r --no-flash --rcm-boot`; `flash.sh` skips `system.img` for RCM boot at 4312. It still prepares recovery assets. `generate_flash_initrd` normally unpacks `bootloader/recovery.img` and copies many tools, ARM64 libraries and matching kernel modules from `rootfs`, including NVMe, SPI, USB, PCI and networking. Omitting the rootfs is not a supported shortcut for this path. The front-end explicitly checks `xmlstarlet`, `sshpass`, `abootimg`, `zstd`; normal shell/Python/DT/CPIO/OpenSSL/udev/IP/SSH dependencies also apply. NVIDIA provides `tools/l4t_flash_prerequisites.sh`, whose package installation mutates the **host**.

## Flags that invalidate the limited preflight

Use the bare `--initrd` workflow, without `--erase-all`, `--direct`, `--boot-rootfs`, injected `-p` options, or inherited customization variables. The observed critical exception is **`--erase-all`**: target `nv_enable_remote.sh` invokes `blkdiscard` during USB gadget setup at 191–201, before the host's initrd-only stop. Explicit external-device waiting has a similar erase branch at 41. `ERASE_QSPI` with `--boot-rootfs` adds a separate QSPI-erasure path. They are unnecessary for inventory. Do not use USB3-recovery fuse programming, `odmfuse`, FSKP, fuseburn, partition-write, capsule-update or normal flash commands for this preflight.

The initrd `/init` mounts RAM/system interfaces and enters `nv_recovery.sh`; without boot-rootfs it starts a shell and kernel-log follower. The host SSH helper then exits before flashing. Once there, suitable inventory commands are `cat /proc/partitions`, `cat /proc/mtd`, and `lsblk -b -o NAME,SIZE,TYPE,MODEL,SERIAL,FSTYPE,MOUNTPOINTS` if available. They need no filesystem mounting or partition modification. Firmware versions reported by newly RCM-loaded components must not be labeled as the preexisting QSPI version.
